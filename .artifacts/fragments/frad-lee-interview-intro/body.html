案例 · 产品设计与 Agent 工程的交叉

三个案例,三种设计决策

金星 AI 看板 · 双产物模型

雷鸟创新 · AI 产品经理

用户用一句话描述需求,AI 解析、预览、确认——看板由此生成。核心设计决策是把 AI 生成的内容拆成两种产物:看板组件(持久展示)与通知触发器(事件驱动,出现即消失)。复合意图由 AI 判定,用户可在预览阶段调整。

为什么不能混在一起?如果一次性提醒也沉淀为看板组件,看板会被事件淹没,「主动查看」的核心价值就不存在了。这个拆分在团队评审后被采纳:第一阶段只做看板组件,通知触发器解耦到后续迭代——节奏更稳,长期也更正确。

AI 会议助手 · 双路径置信度引擎

雷鸟创新 · 桌面原型

实时转写、情绪分析、摘要、任务提取同时运行。关键设计是:情绪显著性只被标注,不进入任务判定路径——一句语气激动说出的待办,依然会被记录,同时附一条敏感度提示,提醒用户回顾当时的语气与上下文。

这解决的是会议工具里「情绪污染任务判定」的问题:情绪是信号,不是过滤器。另一条工程决策是规则驱动的触发批处理——按情绪阈值、超时、发言条数聚合模型调用,在实时感与调用成本之间取平衡。

Code Terrier · 安静,所以被信任

独立产品 · GitHub App,已上架 Marketplace,codeterrier.com

多模型并行 PR 评审产品,正在真实仓库中服役。三个设计决策,也是三条我认为适用于所有 Agent 产品的原则。

  • 精确率优先于召回率

    没有发现问题时,"空"就是正确答案,不硬凑发现。安静的机器人才会被信任;每次误报都在消耗团队对 Agent 的信用额度。

  • 永不批准

    Code Terrier 可以评论、可以请求修改,但批准键永远在人手里。不可逆的决定留给人类——审批应按可逆性分级,而不是按便利性分级。

  • 生产者 / 检查者分离

    发现问题的模型与最终定级的验证器相互独立,验证器持有最终分类权。单一模型既当选手又当裁判,是 Agent 产品里最隐蔽的偏差来源。

Agent 产品形态的四个界面论点

  • 进度 feed 取代进度条

    Agent 的工作是事件流,不是百分比。加载动画假设任务单调且可预估,Agent 任务两者都不是;事件驱动的进度 feed 让用户看到"正在发生什么",而不是"还要等多久"。

  • 过程信息按需解释

    默认不展示推理过程,但用户随时可以追问"你为什么这么做"。可解释性是按需唤起的对话能力,不是一堵日志墙。全量日志墙(Wall of Logs)是把监督成本转嫁回用户。

  • 审批按可逆性分级

    可逆的操作放手自动执行,软确认用于低风险写入,硬确认用于不可逆动作,有些动作永远禁止。Agent 压缩的是点击次数,不是决策点;分级的标准是这个动作能不能撤销。

  • 对话是输入,不是界面

    聊天框是向 Agent 传达意图的输入方式,而界面的主体应该是任务工作台:当前状态、待决事项、产物与历史。Agent 的表面是 agentic surface,决策的表面是 decision surface,两者不该共用同一个容器。

我想在 Kimi 继续回答的问题

当 300 个子代理并行工作时,监督者界面应该长什么样?我的假设是异常聚合视图:哪些子任务偏离了轨道、哪些结论相互冲突——监督者需要的不是 300 个进度条,而是一张"哪里需要我"的地图。
